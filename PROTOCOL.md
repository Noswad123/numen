# Numen local protocol v1

## Overview

Implemented additive local v1 API: newline-delimited JSON over a user-private Unix-domain socket. The first multi-familiar foundation is delivered and verified by automated checks and a three-view Metal smoke test. This is not a stable public SDK. Sources report semantic activity, not animations; an optional built-from-source Djinn interactive adapter publishes through this protocol without OS scanning. Graphical `run` supports lifecycle control; headless `listen` supports discovery/legacy selection, not GUI lifecycle.

## API / Interfaces

### Framing, validation and acknowledgments

Each request is one JSON object terminated by `\n`, at most **8 KiB excluding the newline**. `version: 1` is mandatory on every request; unsupported versions and unknown message types are rejected. Unknown optional fields are tolerated.

Source, instance and activity identifiers contain 1–96 ASCII letters, digits, or `._:-`. Activity records contain:

| Field | Contract |
| --- | --- |
| `activity` | Logical work identifier within the registered source/instance. |
| `sequence` | Positive unsigned 64-bit integer, monotonically increasing per activity. |
| `state` | `idle`, `working`, `waiting`, `succeeded`, `failed`, or `cancelled`. |
| `attention` | Optional boolean, default false. True is allowed only for `waiting`. |
| `reason` | Optional string/null, at most 128 UTF-8 bytes; no control characters or directional embedding/isolate controls. Integration-specific detail, not an animation instruction. |
| `summary` | Optional string/null, at most **160 UTF-8 bytes**, with nonblank trimmed content; no control characters or bidi embedding/isolate controls (U+202A–U+202E, U+2066–U+2069). Explicit producer title/short intent, not generated by Numen. Omitted when serializing None. |

Activity updates are **full-record replacements**, not patches. A present record in `activity.state` or a snapshot with omitted/null `summary` clears its previous summary (subject to normal sequence checks). Repeat the summary on each replacement to retain it. Omitting the entire selected activity from a snapshot instead makes it unavailable and preserves its last selected summary in `Presentation.following`.

`idle` means no active work; `working` means underway; `waiting` means blocked on input or an external dependency. `succeeded`, `failed`, and `cancelled` represent known successful, unsuccessful, and intentional termination respectively. Idle is not success; disconnect is not failure. Do not invent outcomes unavailable from the source.

Each processed complete message receives an ordered JSON-line ACK:

```json
{"version":1,"ok":true}
{"version":1,"ok":false,"error":"stale or duplicate sequence"}
```

`ok` is a boolean; `error` is optional diagnostic text, not a stable error code. Oversized frames, exhausted output buffers, connection limits or deadlines may close a connection without an ACK. An ACK confirms service acceptance, not that a GUI frame was displayed.

### Requests

| `type` | Required fields beyond `version` and `type` | Behavior |
| --- | --- | --- |
| `source.register` | `source`, `instance`, `activities` (array of activity records) | Required before producer events; establishes connection identity and an authoritative initial snapshot. No completion celebration. |
| `activity.state` | Activity record fields | Replaces one activity with a strictly newer sequence; may generate a new success/failure transition cue. |
| `source.heartbeat` | None | Refreshes source liveness without changing activities. |
| `companion.service` | None | Read-only ACK data `{api_version:1, pid, service_instance, graphical, lifecycle, navigation, settings, familiar_count, source_count, diagnostics}` in current services; additive diagnostics, control readiness, not GPU readiness. |
| `companion.quit` | None | Requires graphical shutdown callback; ACK data `{"quitting":true}` schedules global service exit, not source application termination. |
| `source.snapshot` | `activities` | Atomically replaces current activities, subject to sequencing/tombstone checks; no replayed terminal cues. |
| `activity.remove` | `activity`, `sequence` | Removes activity, retaining its sequence tombstone. Sequence must be strictly newer. |
| `companion.status` | Optional nonnegative `offset` (default 0), `familiar` | Returns scoped shared-focused status in ACK `data`; omitted familiar means `main`. |
| `companion.focus` | `source`, `activity`; optional `instance`, `familiar` | Selects exactly one live match not owned by another familiar; clears that familiar's cue and returns scoped status at offset 0. |
| `companion.next` | Optional `familiar` | Cycles eligible lexical live activities, including terminals, with wraparound; clears its cue and returns scoped status. Errors if no eligible records. |
| `companion.reveal` | Optional `familiars` array | Timed reveal of the subset, or all actual current views when omitted/null. Returns legacy status at offset 0, without changing selections. Headless errors. |
| `familiar.list` | Optional nonnegative `offset` (default 0) | Four familiar registry rows per page, including unavailable bindings and capabilities. |
| `companion.targets` | Optional nonnegative `offset`, `familiar` | Four connected protocol-advertised activity rows per page with ownership/eligibility. |
| `familiar.open` | `items` array | Atomically adds 1–16 attached familiars to a graphical service; ACK data `{"opened":["ID"]}`. |
| `familiar.attach` | `items` array | Atomically retargets 1–16 existing familiars; ACK data `{"attached":["ID"]}`. |
| `familiar.close` | `ids` array | Atomically removes 1–16 familiars, not their source applications; ACK data `{"closed":["ID"]}`. |
| `familiar.go-to-mouse` | `ids` array | Starts/restarts live-pointer pursuit for 1–16 unique existing familiar IDs; ACK data `{"moving":["ID"]}` means accepted, not arrived. Requires an installed navigation callback. |

**Identity is connection-scoped.** Only registration supplies `source` and `instance`; subsequent state, heartbeat, snapshot and remove messages operate on that registered identity. Do not use the old draft's source/instance fields on each state message to route updates. A second registration on the same connection is rejected, as is a live duplicate `(source, instance)` on another connection.

Control requests are an exception to producer registration: a standalone control connection need not register or claim a producer slot. Controls also work on a registered connection but **do not refresh producer liveness** or change its registered identity. Unregistered connections still have the two-second connection deadline; controls do not extend it. The source/instance fields in `companion.focus` identify the selection target, not the control client's identity.

Successful controls add `data`: status for legacy selection/reveal controls, paged discovery for list/targets, or lifecycle ID arrays. The CLI prints `data` without the ACK envelope. Familiar identifiers use the same 1–96 ASCII-character rules. Optional `familiar` fields are additive/backward compatible; explicit unknown IDs error. Omitted status/focus/next still scope only to `main`. Once `main` closes, legacy status has null focus without recreating it; focus/next require an existing familiar.

`numen bubbles` sends `companion.reveal` with no subset; `bubbles --familiar main familiar-1` sends `familiars: ["main","familiar-1"]`. A supplied array must contain 1–16 distinct existing IDs, validated before delivery. Reveal changes neither source identity, focus, state, cues nor liveness and never requests activation. “All” is service-local, now across all actual current views, not independent processes. `run --no-bubble` ignores every reveal; ACK is **acceptance, not a displayed frame**. The GUI reveal mailbox is bounded to 32 requests × 16 IDs and preserves subsets; an explicit all request subsumes pending subsets. Headless `Server::start` has no reveal handler and rejects reveal; legacy single-view reveal handlers cannot handle subsets.

The GUI uses `Server::start_graphical_with_settings`, detailed below. Navigation is supplied only after successful macOS `PointerReader` initialization. `on_views` receives initial and changed **complete** `Vec<FamiliarPresentation>` snapshots (`{id, preset, presentation, settings}`); `on_reveal` receives `Option<Vec<String>>`; navigation receives `Vec<String>`; quit has no arguments. Callbacks run on the worker and must promptly enqueue/coalesce bounded UI work, not perform OS work. `FamiliarControl::next(id)`, `close(id)` and `settings(id, patch)` are bounded nonblocking GUI commands. Legacy headless output remains a `Presentation` for `main`, without settings.

### Runtime settings

The macOS familiar click menu is a local GUI control surface, **not a new wire request** and not a replacement for the fzf `numen menu`. Left-click release opens it; right-click opens the same menu rather than cycling Preview. Non-macOS keeps old left-drag/right-cycle; digits 1–9 are unchanged. No source update opens a menu and producers gain no source-execution authority.

Native Settings uses the same three existing fields/preset sets as fzf, with one-field `SettingsPatch` selections. `FamiliarControl::settings(id, patch)` validates ID/patch and uses the shared nonblocking 32-entry command channel. Queue acceptance is not commit: the worker rechecks support/existence, applies canonical `Store::settings`, then publishes complete snapshots. Checkmarks/custom numeric rows use canonical `f64` values, never renderer `f32` or optimistic local values. Manual/demo have no settings IPC or navigation, but pause, permitted reveal, Close and Quit remain possible.

Show status respects `--no-bubble`; Go to mouse and Pause/Resume target only the clicked view (navigation requires pointer availability). Close familiar uses existing scoped close/retry behavior, retaining the last-close service. Quit Numen (all familiars) takes normal root shutdown, independent of clicked-target existence, never stopping Djinn. After synchronous native tracking, latest registry and familiar ID/WindowId are revalidated; stale/failed/closing per-view actions are ignored. A 25 ms native timer cancels the popup on target removal, external quit or `--exit-after`, not ordinary source changes. Rust GUI ticks pause during tracking; opening/dismissal preserves cue/manual override/pause/navigation and rebases motion clocks. See [gesture and example details](README.md#native-familiar-menu-macos).

Additive v1 request: `familiar.settings {ids, patch}`. Both fields are required/non-null. `ids` must contain **1–16 unique valid existing familiar IDs**; there is no implicit all. `patch` accepts any nonempty subset of the fields below. Supplied values must be finite numbers; nulls, strings, unknown patch keys, empty patches and invalid bounds reject the whole request. This strict patch is an exception to general optional-field tolerance.

| Field | Inclusive bounds | Default | Units |
| --- | --- | --- | --- |
| `sprite_scale` | 0.25–2 | 0.5 | Character-only multiplier |
| `font_size` | 8–32 | 12 | Logical canvas units |
| `bubble_duration` | 0.25–30 | 5 | Seconds |

Omitted fields retain each familiar's own values. All IDs and the patch validate before any mutation; an unknown/closed ID rejects the entire batch. Success ACK data is `{"updated":["main"]}`, exactly the requested IDs in request order. CLI/menu verify the returned set without duplicates. Optional root `service_instance` is checked before mutation. No producer registration is needed; settings do not refresh source liveness or alter attachment, cues or activity state.

`familiar.list` rows additionally contain complete `settings: {sprite_scale, font_size, bubble_duration}`. The server advertises `settings` only for the new graphical constructor, independently of navigation. Headless and legacy constructors reject edits even when discovery includes values. Read through `numen familiars`; there is no settings-get CLI.

Current GUI API: `Server::start_graphical_with_settings(path, on_views, on_reveal, optional_on_go_to_mouse, on_quit, bootstrap_main, settings: FamiliarSettings)`. Complete settings validate before listener creation. `on_views` receives complete `Vec<FamiliarPresentation>` snapshots with `{id, preset, presentation, settings}`. The legacy `#[cfg(test)] start_graphical` has the same arguments except settings, includes shutdown, but rejects settings; other compatibility constructors retain their existing callback behavior. Callbacks enqueue bounded work promptly, never perform OS work on the worker.

Registry settings are independent of `Presentation` and retained in latest-only snapshots. Actual `RunOptions` seed immutable original defaults for Main and future Opens, including empty startup; editing Main does not change future defaults. GUI edits preserve Preview/manual override, pause, player and navigation. Font/sprite changes redraw with per-view caches/layout; sprite resizing preserves physical foot-center and saved hidden restoration where possible without focus. Duration changes affect future accepted reveals/notifications only: no hidden reveal, current-deadline retiming, quiet/history reset or disabled/always-policy change. All settings are runtime-only, not persistent preferences, characters/variants or placement controls.

```json
{"version":1,"type":"familiar.settings","service_instance":"service-1","ids":["main"],"patch":{"sprite_scale":0.5,"font_size":16,"bubble_duration":5}}
{"version":1,"ok":true,"data":{"updated":["main"]}}
```

CLI equivalent: `numen settings --familiar main --sprite-scale .5 --font-size 16 --bubble-duration 5`; any nonempty flag subset is valid. Rebuilding does not upgrade an older running service: explicitly run `numen quit`, then `numen menu` → Open existing chat once after deployment. No Djinn restart is needed; subsequent runtime edits need no restart. Never automatically quit/replace the user's service.

### Service readiness and graceful quit

`numen service-info` sends `companion.service` without additional fields. API version remains 1; data has `api_version`, nonzero `pid`, unique `service_instance`, `graphical`, `lifecycle`, and `navigation`, plus the additive fields below in current services, with no shutdown flag. Capability booleans describe control handlers, not GPU/frame readiness. The query does not mutate sources or refresh producer liveness; its PID is information, never authorization to signal a process.

### Read-only diagnostics

`companion.service` adds the following without changing protocol/API version 1:

| Field | Contract |
| --- | --- |
| `settings` | Boolean: graphical settings handler support. |
| `familiar_count` | Logical familiar registry size, including unavailable bindings; not native-window count. |
| `source_count` | Registered protocol source count; not OS-process count. |
| `diagnostics` | `{version:1, executable, build, hotkeys}`; independent diagnostics schema version. |
| `diagnostics.executable` | Service's own executable path or null if unavailable/unsafe to report; bounded to 1024 UTF-8 bytes, control/bidi-free. |
| `diagnostics.build` | `{version, fingerprint, source_fingerprint, target, profile}` embedded in the responding service, not read from a replacement executable on disk. |
| `diagnostics.hotkeys` | `{option_i:{state,reason}, option_m:{state,reason}}`, actual live registration facts, not delivery guarantees. |

Wire names are snake_case. Allowlisted valid status/reason pairs (`reason` is null for registered):

| `state` | `reason` |
| --- | --- |
| `registered` | null |
| `disabled` | `no_hotkey`; `no_bubble` for I only |
| `unsupported` | `unsupported_platform`; `unsupported_mode` for M only |
| `unavailable` | `registration_failed`, `headless`; `pointer_initialization_failed` for M only |
| `uninitialized` | `registration_pending`, `not_reported` |

The service shares a live `RuntimeDiagnostics` handle (`Arc<Mutex<Snapshot>>`) with GUI registration. Queries copy its current snapshot, not frozen startup results. Logical counts come from the current Store. No raw argv, environment values, source identities or activity summaries enter this diagnostics payload. Build flags/compiler details are hashed, not exposed; [fingerprint coverage and exclusions](ARCHITECTURE.md#recorded-build-identity) apply.

`numen doctor [--json]` sends exactly one bounded `companion.service` query, with no registration or follow-up mutation. It preserves private-socket checks and existing 500 ms connection/write/ACK bounds; it never starts/signals processes, creates directories/logs, reveals, edits settings, changes registration or refreshes source TTL. Human output is the default; JSON report fields are `client: {executable,build}`, `socket`, `service`, `service_state`, and `build_comparison`. `service` is null offline; otherwise it includes the metadata fields above (optional additive fields may be null for older services).

`service_state` is `reachable` for validated diagnostics v1, `not_running` for missing/refused sockets, `legacy` when diagnostics is absent, or `unsupported_diagnostics` for another unsigned diagnostics version. Legacy/future schemas leave service build/hotkeys unknown (`diagnostics: null` in the report); current v1 requires settings/counts and valid build/hotkey fields. Malformed metadata, invalid/contradictory known state/reason pairs and duplicate JSON keys at any nesting depth are errors, not legacy/offline fallbacks. Rejected peer strings are not echoed in doctor errors.

The recorded-build comparison is serialized as `build_comparison: "match" | "different" | "unknown"`: it compares recognized embedded build fingerprints, not executable bytes or age. Missing/legacy/unsupported diagnostics or unknown fingerprints yield unknown. A match covers recorded inputs only; same package version/path alone is insufficient, and different is not newer/older. Offline/legacy/unsupported/different are informational exit 0; unsafe paths, other errors, timeouts and malformed replies exit 1. `--json` does not turn failures into a successful report.

```sh
numen doctor
numen doctor --json
numen --socket /absolute/private/events.sock doctor --json
```

An updated client can diagnose a legacy service immediately. An old running service cannot report newly added fields until one user-chosen Numen restart; installing/rebuilding does not upgrade it in place, and doctor never restarts it. No Djinn restart is required for diagnostics.

### Generation preconditions and shutdown

Any request may include optional **root** `service_instance` using the same 1–96 ASCII identifier rules. If present it must exactly match this listener's instance; mismatch rejects before source/control mutation, liveness refresh or callback, with `service instance changed; reopen menu`. The menu pins discovery metadata and seals all subsequent RPCs, never repinning stale selected IDs after restart. New menus require instance metadata; older services must be restarted. One-shot CLI clients and producers may omit the precondition for compatibility. This per-listener generation identity is distinct from producer `instance`, is not persisted, and is not an authentication secret; private socket ownership/permissions remain the access boundary.

`numen quit` sends `companion.quit` without additional fields. Current graphical startup installs the shutdown callback; headless/legacy handlers without one reject it. Success is `{"version":1,"ok":true,"data":{"quitting":true}}`: scheduled, not completed. After ACK flush, callback delivery waits for client EOF or 500 ms; later pipelined input is ignored. A coalesced root `AppEvent::QuitService` exits even with zero windows, drops all views and releases the server/owned socket/global hotkey. No source applications are terminated and no metadata PID is killed. Close remains per-view and last-close retains the service.

Only offline **menu** Open can bootstrap detached current-executable `run --empty` (unless `--no-start`), with a five-second control-readiness bound. Discovery alone never spawns or writes files. Direct CLI/wire Open still needs a running graphical service. `run --empty` uses `Store::empty()`: no unattached `main` appears, even on source updates; it conflicts with manual/demo. Concurrent startup reuses the UDS winner; headless/outdated/unsafe existing services are never replaced or killed. See [Wisp](WISP.md) and [architecture](ARCHITECTURE.md#menu-bootstrap-and-quit).

`numen go-to-mouse --familiar ID1 ID2` sends `familiar.go-to-mouse` with `ids`, not `familiars`. The field is required and non-null: 1–16 distinct valid IDs, each existing at dispatch. Missing/empty arrays, duplicates, invalid IDs and unknown/closed IDs reject the entire request before any callback; there is no implicit all or partial delivery. Unsupported handlers (including headless and old `start_with_familiars`) reject with `go-to-mouse requires graphical navigation support`. Success is `{"version":1,"ok":true,"data":{"moving":["ID1","ID2"]}}`; no arrival/completion event or guarantee is implied. Like other controls, this requires no producer registration and does not refresh liveness or mutate bindings/activity state.

Navigation delivery uses a bounded GUI queue (32 requests × 16 IDs), coalesces pending target sets, and applies the newest registry snapshot before starting views. Reissue restarts intent; a closing/failed view may disappear after acceptance. Current support is macOS only. Hard deadline gates bound fresh read-only pointer sampling and physics. Contact matches the compositor's physical sprite-alpha raster and requires actual native feedback against a held pose; predicted movement is not arrival. Success jumps once, then the latest attached emotes resume without expired cues or ongoing follow. No agent success is published. Space pauses motion/animation, not bubble deadlines; occlusion alone does not suspend pursuit or celebration. Actual native drag, digits, non-macOS right-cycle, L, Tab and close cancel without success; macOS menu opening/dismissal and reveal-all do not. See [coordinate details](ARCHITECTURE.md#navigation-and-coordinate-contract).

Global **Option+M** is a GUI-only service-local broadcast, not a new wire request or permission to omit `ids`. Its callback queues all-current intent; the main GUI loop first applies the latest registry, then starts eligible views and skips closing/failed ones. With zero views it does nothing and remains registered for later Open. Focused local exact Alt+M moves only the focused view if global M registration failed/was disabled; successful global M suppresses local delivery independently of I. Both preserve pause and never request activation/focus. Pointer initialization failure, non-macOS and manual/demo sessions have no M/navigation support.

```json
{"version":1,"ok":true,"data":{"mode":"shared-focused","focus":{"source":"djinn","instance":"producer-1","activity":"chatid"},"focus_available":true,"activities":[{"source":"djinn","instance":"producer-1","activity":"chatid","state":"working","attention":false,"reason":null,"summary":"Investigating retry backoff"}],"offset":0,"total":1,"next_offset":null}}
```

`focus` is null before an activity has ever been selected; otherwise it is the exact `{source, instance, activity}` pin, even if unavailable. `focus_available` reports whether that record is currently present. `activities` contains up to **4** live `Selection` records, in lexical `(source, instance, activity)` order, including terminal states but excluding tombstones. Each selection has the fields shown above (no sequence); `summary` is optional and omitted when absent. `offset` echoes the requested index; `total` counts all live records; `next_offset` is the next page index or null. Out-of-range offsets return an empty page. Pages are current views, not an atomic multi-request snapshot; concurrent producer updates may change them. Four-record pages keep worst-case control ACKs, including summaries, below 8 KiB.

Explicit scoped status additionally includes `familiar_id`. `activities` still lists canonical live activities, not just eligible targets. Use discovery ownership fields when building a selector.

### Discovery and lifecycle

`familiar.list` data is `{familiars, offset, total, next_offset}`. Each row has `id`, `preset`, `attachment` (exact tuple or null), `available`, optional cached `summary`, complete `settings`, and `capabilities`. Multi-familiar GUI rows advertise `info`, `attach`, `close`, plus `settings` with the new constructor and `go-to-mouse` with navigation, independently. Headless/legacy non-multi handlers advertise `[]`; old graphical test helpers retain their existing GUI capabilities but omit settings. Server-side advertisement matches installed handlers, not source capability claims. Other platforms currently omit navigation.

`companion.targets` data is `{targets, offset, total, next_offset}`. Rows flatten the Selection fields above and add `claimed_by` (ID or null) and `eligible` (boolean). Only currently connected protocol-advertised activities appear, including terminals; unavailable waiting pins are not live targets but still reserve ownership. Eligibility means unclaimed, or already owned by the supplied familiar. The menu fetches fresh pages per selection, filters ineligible rows and excludes earlier pending choices. Discovery itself is not an adapter or OS scan; the optional Djinn adapter supplies ordinary protocol records, enabled by default for supported local interactive chats in updated builds. Both discovery endpoints page four rows with the same paging semantics as status.

Open items are `{id?, preset?, source, instance?, activity}`; preset defaults to `djinn`, the only supported preset. Attach items are `{id, source, instance?, activity}`. Targets are **flattened inside each item**, not nested or a shared batch target. IDs for presets and active familiars occupy different concepts. Offline CLI `presets` returns `{"presets":[{"id":"djinn","name":"Djinn","capabilities":["open"]}]}` without contacting a service.

Open/Attach/Close require the multi-familiar graphical handler, not headless `listen` or a legacy reveal-only handler. Open does not bootstrap the service. Each Open/Attach entry resolves exactly one currently live `(source, instance, activity)`; omitted instance errors if ambiguous. Ownership is exclusive across all familiars, **including disconnected waiting pins**. Unknown presets, duplicate IDs/targets, unavailable/ambiguous targets or ownership conflicts reject the entire batch with no changes. Close likewise validates every distinct existing ID first. Attach allows reselecting one's own target, but cannot take a target currently held by another familiar even if that owner is in the same batch: swaps are rejected. Validation is repeated at mutation, not trusted from a previous discovery page. Sources are never executed or stopped.

At most **16 active familiars**, including bootstrap `main`. Generated `familiar-N` IDs increase monotonically over the service lifetime without accumulating generated-ID history. Explicit-ID history is limited to 256 IDs plus reserved `main` (257 history entries total). Closed IDs cannot be reused, including generated IDs. Omit Open `id` to continue using generated IDs after explicit history fills. All state is ephemeral; restart resets IDs and no persistent profiles exist.

Lifecycle ACKs confirm atomic registry acceptance, not GPU readiness. Complete snapshots drive asynchronous native-window/surface creation; a failure can remove the affected view after Open succeeded. Q/Esc/native close addresses only that familiar. Last-close leaves IPC/hotkey alive with zero windows; later Open remains valid. Manual/demo are socket-free single-view sessions whose close exits the process. Ctrl-C quits the service.

## Data Flow

1. Producers connect and successfully register within **2 seconds** of connection acceptance, including a fresh authoritative activity snapshot (possibly empty). Standalone control clients may exchange controls without registration within that deadline.
2. Send updates/snapshots and heartbeats. Successfully applied producer events refresh liveness; after **10 seconds** without one the source expires and its connection is removed. Invalid/stale messages and companion control requests do not refresh it.
3. State/remove updates must have strictly greater sequences than existing records, including tombstones. Duplicate and stale updates are rejected.
4. A snapshot is checked atomically: lower sequences are rejected; equal sequences are allowed only for an identical still-present record. Equal-sequence changed records or resurrection of tombstones are rejected. Omitted activities are removed, retaining their previous sequence tombstones. Newer records can restore removed IDs.
5. Disconnect removes the source and its cues immediately when the connection is retired; no stale attention or inferred outcome remains. The exact focus pin remains, unavailable, with no automatic fallback. Reconnect registers afresh with the current authoritative snapshot. A restarted producer should use a new instance ID; a new instance does not inherit the old focus. Registration/snapshots do not celebrate historical terminal states.

### Optional Djinn producer

Djinn's local owning-Worker interactive adapter uses source `djinn`, a backend-lifetime UUID instance stable across socket reconnects, and the actual UI `SessionID` as activity. Chat-tab viewer presence renews every 5 seconds (20-second TTL); opening an existing idle chat is sufficient. Leaving Chat removes idle records, while previously observed busy records remain until idle. Dashboard/history do not advertise new targets. Reload/new backend means a new instance and explicit reattachment; exit/disconnect makes exact pins unavailable.

The adapter sends authoritative snapshots, heartbeats and eligible live state transitions. Permission/question requests map to `waiting` with attention, retry to `waiting` without attention; otherwise activity is `idle`/`working`. Internal response-owned/settled events add completed response → `succeeded` with `response_completed`, final assistant non-abort error or failure/defect → `failed` with `run_failed`, and winning explicit user cancellation → `cancelled` with `run_cancelled`. Normal stop/length final assistant completion is response completion, not proof of task success. Missing finish, tool-calls, unfinished/non-assistant results, error events, individual tool/model steps, idle, disconnect and shell completion/nonzero exit do not establish response outcomes. Abandoned teardown/interruption without user cancellation is neutral idle; final non-abort assistant errors/defects take precedence over cancellation. No public Schema/SDK or Numen Rust renderer changes are required.

Mid-run admission captures the current owner; opening settled history does not replay outcomes. Ownership order protects a newer B owner from late A cancellation; joined callers share one outcome. Viewed terminal bases persist until new work/external busy, while unviewed observed terminals are retained 5 seconds then removed. Reload abandons ownership. Reconciliation polls every 250 ms and can take about 500 ms after an event, not hard real-time. Adapter admission is 16 current sessions and 32 distinct IDs over the backend/transport lifetime, including removed IDs; it fails closed without ID reassignment. Restart the backend and reattach to reset lifetime capacity. These adapter limits are distinct from the protocol's source/view limits below.

The adapter guarantees at-most-once **live cue submission**, not exactly-once GUI animation. Service and transport each bound live queues to 32 events with 2-second expiry; ACK waits are capped at 500 ms. The service seals the ACKed `transport.connection()` generation at event time. Offline, unACKed-registration and prior-generation events become authoritative snapshot-only state; overflow, expiry and lost ACKs fail closed, dropping cues without reconnect replay. Terminal registration/snapshots show Completed/Failed/Cancelled under the existing presentation policy without historical cues. Cancellation never celebrates; success cannot hide active failure/attention. See the [Djinn guide](../djinn/docs/numen.md) for internal interfaces and package-local checks, including opt-in headless real-wire tests via `NUMEN_TEST_BINARY=/absolute/path/to/numen` (`1` is a developer-local convenience). A separate real TUI → fzf → native idle-familiar smoke passed; live model-outcome GUI animation, full visual/focus acceptance and Wisp palette → Kitty handoff remain manual checks.

Discovery is on by default for the supported local ordinary interactive UI in an updated Djinn build: use plain `djinn` and select a Chat tab, `djinn -s REF`, or `djinn session chat REF`, without an enablement export. An already-running older Djinn UI needs one restart with the updated binary; rebuilding alone does not update it. Reopen the chat and explicitly reattach if the backend instance changed. Source fallback launches must run Bun from `clients/djinn-ui/packages/opencode` to load its OpenTUI/Solid preload, also without an enablement flag.

`DJINN_NUMEN_DISABLED=1` explicitly opts out of reporting; legacy `DJINN_NUMEN=0` remains supported. Missing enablement defaults true and missing disablement defaults false. Both parse exactly `true/yes/on/1/y` as true or `false/no/off/0/n` as false, case-sensitive without trimming; malformed enablement becomes false and malformed disablement becomes true. Effective enablement is the parsed enable flag AND NOT the parsed disable flag, shared by CLI and backend. This policy changes no v1 wire fields.

`DJINN_NUMEN_SOCKET` must be an absolute existing private endpoint matching Numen `--socket`; defaults match the XDG/UID-temporary path below. Discovery neither starts Numen nor opens familiars, publishes history, reads raw prompts, changes Wisp/transcripts or makes model calls; menu Open may start Numen and the adapter retries by default every second. Only explicit current Chat selections and previously observed busy chats (plus bounded terminal retention) are reported, not all Djinn OS processes. Titles/status are shared automatically and may be sensitive; opt out to prevent reporting, while `--no-bubble` hides display only. Rust-native ask/session run, mini, external attach, remote web, current core v2 API and arbitrary background/child sessions remain outside its scope. See [setup and privacy](README.md#optional-djinn-interactive-adapter).

### Presentation policy

Each familiar implements **shared-focused** semantics: one selected activity, never aggregate work. Only bootstrap `main` auto-chooses the first unclaimed live activity once, lexically among records arriving together. Later arrivals cannot steal selection. Each exact pin survives removal, snapshot omission, disconnect and expiry with no base; it retains ownership while resting until explicit selection/next or that exact record returns. There is no OS-focus inference.

`companion.focus` requires exactly one live match not owned by another familiar; missing/ambiguous/conflicting matches leave the pin unchanged. Include `instance` to disambiguate. `companion.next` cycles eligible live records, including terminals, in lexical `(source, instance, activity)` order; an unavailable pin starts at the first eligible record. Selection clears only that familiar's cue without historical celebration. Background updates cannot take over. Bindings, cues and summary caches are per familiar over one canonical activity store.

Only new `activity.state` transitions of the focused activity into succeeded/failed generate a **1.5-second** cue. Repeating the same terminal state with a newer sequence does not replay it. Failure replaces success; success cannot hide an active failure cue. Focused attention clears/drops cues, never queues them for later. Cancelled, idle, removal and disconnect do not generate completion cues.

`Presentation {base, cue, following?}` preserves the focused record's identity even when its base state is terminal. Optional `following` has `{source, instance, activity, summary?, available}`; it retains the exact pin and last selected summary through removal, snapshot omission, disconnect and expiry. When unavailable, `base` and `cue` are null but `following.available` is false: this is not an unfocused presentation. Before selection, `following` is None and omitted (the default is `{"base":null,"cue":null}`). Focus changes replace the summary cache, including with None, so another chat's text cannot carry over. Background updates do not affect it.

The GUI translates semantic states independently: external waiting → `review`, attention waiting → `waiting`, terminal base → idle. Fresh terminal cues play once, then rest unless the same focused activity has already resumed work. There is no restoration to other background work. When visible, the bubble shows selected identity, summary (activity ID fallback), and **current base status**, not a transient cue: Idle, Working, Needs your input, Waiting on dependency, Completed, Failed, Cancelled, or Unavailable. With no selection it says Choose a conversation / Not following. Manual/demo expression overrides are visibly labeled Preview. Metadata-only changes repaint even while paused or on the same animation, without restarting animation or requesting focus.

Visibility is local GUI policy, not a producer field. It starts hidden; first selection/new focus and selected status/summary changes show brief notifications (default five seconds). Initial empty No conversation, heartbeats, reason-only changes, cue expiry and background updates do not notify. Automatic changes while visible do not extend the deadline. After expiry, 750 ms quiet time suppresses automatic changes without queueing them; explicit reveal/new focus bypasses quiet time and refreshes the duration. Hide runs even when paused/occluded. `--bubble-duration` accepts finite 0.25–30 seconds; `--always-bubble` opts into persistent debug/preview display and conflicts with hard-disable `--no-bubble`.

Global macOS Option+I (Alt+I) still reveals all current views; focused local fallback reveals that view. CLI `bubbles` supports all or a subset. Option+I and Option+M register independently once per process through one shared main-thread Carbon manager (`global-hotkey` 0.9), not all-keystroke capture/EventTap. One capture-free dispatcher has two weak targets and independent repeat latches until matching release. A collision warns nonfatally without disabling the other key; choose `--socket PATH` for CLI targeting. `--no-hotkey` disables both global registrations but retains focused local I/M and CLI controls where supported. `--no-bubble` skips only global I and ignores every reveal without redacting metadata; global M remains eligible. Chords may override OS shortcuts. Bounded private zero-view native registration and normal-exit cleanup passed all four [smoke cases](README.md#final-optionm-validation); collision handling was tested deterministically, not with real OS collisions. Actual OS presses/background-focus delivery and hotkey-driven motion remain unverified, with no synthetic OS keys, input taps, permission requests or existing-user-service control/restarts. Native unregister is best-effort; see [cleanup limitation](ARCHITECTURE.md#live-display-and-output).

A latest-only mailbox coalesces presentations with one pending GUI wake; acceptance is not an animation queue. Manual expression override is separate from service selection: L resumes the current selected base without changing conversation or replaying a cue; Tab queues next-selection and resumes live control. Both require a live-enabled GUI session.

Tab/L reveal that view on live resume; 1–9 (and non-macOS right-click) reveal its Preview. On macOS right-click opens the native menu. Demo cycling does not auto-reveal. Initial `main` can request startup focus with `--focus`; non-macOS left-click retains its explicit focus/drag request. Later Open, notifications and reveal never request focus; actual native menu/drag focus acceptance remains manual.

## Edge Cases

### Bounds and EOF

- At most **16 registered sources** and **24 total connections** (`MAX_CLIENTS = MAX_SOURCES + 8`), including unregistered and standalone control clients. This leaves eight additional client slots beyond full producer capacity, not an unlimited or separately reserved control pool. At most **32 distinct activity IDs per source lifetime**, including removed/omitted tombstones; snapshots cannot contain duplicate IDs or more than 32 records.
- One nonblocking worker polls every **25 ms**, with one bounded read and at most **8 messages per client per tick**. Input is bounded to 8 KiB plus the newline allowance; queued output is bounded to 16 KiB. There is no Tokio runtime or unbounded event log.
- GUI `FamiliarControl::next(id)` / `close(id)` / `settings(id, patch)` share a **32-entry** channel with nonblocking `try_send`; at most eight commands are processed per worker tick. Tab resumes after enqueue, not acknowledged selection. Close intent retries on saturation; accepted closes wait for registry snapshot removal without repeated submission. Settings saturation reports failure without an optimistic edit; worker rejection of unsupported/closed IDs is logged and discarded. Native/GPU failure closes only its failed live view; common font initialization remains fatal. Per-view hide/pause deadlines are independent; the global exit deadline survives zero views and cancels native menu tracking.
- Write-half-close drains complete buffered frames and ordered ACKs for up to **2 seconds**; an incomplete trailing EOF frame is discarded, not parsed. Full EOF retires the source after draining (or the drain deadline); a peer unable to receive ACKs cannot hold it indefinitely.
- `listen` emits JSON `Presentation` changes (`base`, `cue`, optional `following`), not raw requests or every ACK. Latest-only coalescing and a detached stdout writer prevent an unread pipe from blocking the service/deadline. Intermediate views may be missed; the latest pending view is retained. Shutdown may truncate the last diagnostic line if the writer is blocked.

### Summary display and privacy

Numen makes no LLM calls, reads no transcripts and automatically copies no raw prompts. The optional Djinn adapter uses only the existing chat title, sanitized, trimmed and capped at 160 UTF-8 bytes; it makes no LLM calls and copies no raw prompts or error files. Summaries can still be sensitive on screen. `run --no-bubble` hides only the on-screen bubble, not summaries in wire/state or diagnostic output.

Display typography is a local GUI concern, adjustable through familiar settings controls, not producer activity fields or instructions. The physical-pixel CPU compositor uses `fontdue` advances, kerning, metrics and antialiased coverage, not bitmap cells or full-canvas nearest upscaling. Identity/status are clipped by measured width; summaries wrap to at most three lines according to available space/line height, with U+2026 `…` truncation. Larger fonts may reduce visible lines without resizing the sprite. These display limits do not truncate stored UTF-8 metadata or change the 160-byte validation limit.

The default face is installed SauceCodePro Nerd Font Regular, discovered through `fontdb` system/user directories, with embedded OFL Source Code Pro Regular as fallback if the default is unavailable. No Kitty configuration is parsed at runtime. Explicit `run --font-family NAME` (exact Normal/Regular face) or `--font-file PATH` (face/index 0) errors on missing/invalid selection; they conflict. `--font-size` is finite 8–32, default 12 logical units scaled with the scene/display. Unicode/Nerd icon coverage depends on the face; missing glyphs use its U+FFFD, then `?`, then `.notdef`. No full script shaping, color emoji or fallback-font chain exists. See [font selection and limits](assets/fonts/README.md).

`run --sprite-scale` is also local presentation configuration: finite 0.25–2, default 0.5, independent of bubble/text. The native window starts at 96 × 104 logical units, expands to 384 × 248 while revealed, and shrinks back with no hidden full-bubble input area. Native atlas cells remain 192 × 208; `--sprite-scale 1` gives 192 × 208 hidden or 384 × 352 revealed. Geometry preserves the sprite anchor where possible, clamps expansion to current monitor bounds, and restores the saved hidden position unless an explicit left-drag commits a new location; unsupported positioning is best-effort. `--scale` remains the whole-scene multiplier, default 1.5, including the font; text is rasterized at font size times actual physical scene scale. None of these options changes wire fields, source metadata, selection or payload limits.

Bubble-capable GUIs load fonts once at initialization even while initially hidden. `--no-bubble` skips font lookup/loading even for an unusable family/file (CLI validation still applies), but does not redact metadata. `listen`, `publish`, `status`, `focus`, `bubbles`, `check-assets`, and `font-license` never initialize fonts; `font-license` prints the full embedded SIL OFL 1.1 text without a GUI.

### Socket paths and ownership

Global `--socket PATH` works before or after the command. Without it, a nonempty `XDG_RUNTIME_DIR` selects `$XDG_RUNTIME_DIR/numen/events.sock`; otherwise use `std::env::temp_dir()/numen-UID/events.sock` with the effective UID. Paths must name a socket file, contain no NUL, and be at most **100 bytes**.

The parent must be a user-owned private directory (use **0700**), not a symlink. The server creates only that leaf directory if its ancestor already exists; it never recursively creates ancestors or chmods an existing directory. The publisher requires the parent to exist. The server creates a user-owned **0600** socket; the publisher checks ownership/type and rejects group/other permissions.

An active listener collision refuses startup. Only a user-owned socket whose bounded connection probe returns connection-refused is eligible for stale replacement, with an inode/device recheck. Other probe failures, foreign files and symlinks are not permission to unlink. Normal server drop removes only its owned matching inode; abrupt termination may leave a stale socket, recoverable at the next startup.

### Publisher scope

The bundled synchronous publisher bounds connection, write and ACK waits to 500 ms as applicable and validates ACKs. It reports errors/nonzero exit rather than silently ignoring them. Its synchronous stderr logging can still block. It is an interactive diagnostic, not a safe automatic agent callback or stable best-effort SDK. Adapters must isolate publishing from source execution and recover current state via snapshots; the optional Djinn transport is separate from this diagnostic command.

## Example usage

Service-only controls need no producer registration:

```json
{"version":1,"type":"companion.service"}
```

On a separate connection, `{"version":1,"type":"companion.quit"}` schedules graphical shutdown. Do not pipeline further controls after quit. CLI equivalents are `./target/debug/numen service-info` and `./target/debug/numen quit`.

After a debug build, start `./target/debug/numen run`, or use `./target/debug/numen listen --exit-after 5` for headless diagnostics. In another terminal:

```sh
./target/debug/numen publish --state working --source build --summary 'Investigating retry backoff' --duration 5
./target/debug/numen publish --state waiting --attention --reason permission_required
./target/debug/numen publish --demo
# While producers are connected:
./target/debug/numen status --offset 0
./target/debug/numen status --offset 4
./target/debug/numen focus --source djinn --activity chatid --instance producer-1
./target/debug/numen focus --next
./target/debug/numen bubbles # Graphical run only; brief reveal without changing selection
./target/debug/numen go-to-mouse --familiar main # Navigation-capable graphical run only
./target/debug/numen --socket /path/to/private/events.sock bubbles
```

Defaults are source `diagnostic`, activity `task`, generated PID/time instance and three seconds per state. Each state is held while connected, with approximately one-second heartbeats. Demo sends working → waiting/attention → succeeded → working → failed → cancelled → idle. After the final hold it removes the activity with a newer sequence and disconnects. No GUI or asset decoding is needed for publishing.

`publish --summary` validates the supplied value, then trims surrounding whitespace and repeats it on every state, including with `--demo`. The wire API accepts surrounding whitespace but requires nonblank content; it does not trim stored metadata.

Illustrative requests on **one persistent connection**, each followed by its ACK:

```json
{"version":1,"type":"source.register","source":"build","instance":"build-42","activities":[{"activity":"task","sequence":1,"state":"working","summary":"Investigating retry backoff"}]}
{"version":1,"type":"activity.state","activity":"task","sequence":2,"state":"waiting","attention":true,"reason":"permission_required","summary":"Investigating retry backoff"}
{"version":1,"type":"source.heartbeat"}
{"version":1,"type":"source.snapshot","activities":[{"activity":"task","sequence":3,"state":"working"}]}
{"version":1,"type":"activity.state","activity":"task","sequence":4,"state":"succeeded"}
{"version":1,"type":"activity.remove","activity":"task","sequence":5}
```

The registration snapshot expresses current truth without a cue; the subsequent successful state transition can cue completion. Keep the connection alive while representing work—opening a new connection for every line does not preserve the identity or activities.

The sequence-3 snapshot above omits `summary` on its present record, clearing the previous summary; the bubble then falls back to `task`.

Control-only connection examples (no `source.register` needed; focus/next require existing targets, reveal requires a graphical service):

```json
{"version":1,"type":"companion.status"}
{"version":1,"type":"companion.status","offset":4}
{"version":1,"type":"companion.focus","source":"djinn","activity":"chatid","instance":"producer-1"}
{"version":1,"type":"companion.next"}
{"version":1,"type":"companion.reveal"}
{"version":1,"type":"familiar.list","offset":0}
{"version":1,"type":"companion.targets","familiar":"main","offset":0}
{"version":1,"type":"familiar.open","items":[{"id":"build-pet","preset":"djinn","source":"build","instance":"worker-2","activity":"task"}]}
{"version":1,"type":"companion.status","familiar":"build-pet"}
{"version":1,"type":"companion.reveal","familiars":["build-pet"]}
{"version":1,"type":"familiar.go-to-mouse","ids":["main","build-pet"]}
{"version":1,"type":"familiar.attach","items":[{"id":"build-pet","source":"build","instance":"worker-3","activity":"task"}]}
{"version":1,"type":"familiar.close","ids":["build-pet"]}
```

Open/Attach examples require distinct, connected, eligible targets at mutation time. CLI equivalents are `open --source build --instance worker-2 --activity task --id build-pet` and `attach --familiar build-pet --source build --instance worker-3 --activity task`. For multiple selections, `open --batch FILE` / `attach --batch FILE` (or `--batch -` for stdin) reads a **root JSON array** of the corresponding item objects, not a request envelope; use `id`, not `familiar`, inside items. Batch input and the final request envelope must both fit the 8 KiB limit. `close --familiar ID1 ID2` sends an atomic close batch.
